# 数据维护任务持久化设计

## 背景与问题

“数据维护 → 补齐任务 → 一键初始化/补齐全部指数”在当前实现中由页面内的 `MaintenanceTaskStatus` 驱动。刷新、重新打开页面或断开浏览器连接后，该对象会被重新创建，用户看不到原任务的进度、结果或失败原因。指数批量补齐也没有逐项进度回调。

此外，指数历史存在旧文件但拉取未返回新增交易日时，服务会把旧文件重新写回并记录 `SUCCESS`。任务“完成”不代表数据已达到目标交易日，造成 11 个行情滞后指数被误报为成功。

## 目标

在不引入外部消息队列的前提下，让本地 NiceGUI 维护任务具备：

- 浏览器刷新后可恢复显示的运行状态、逐项进度、结果摘要和错误；
- 与页面生命周期解耦的服务端后台执行；
- 同类指数全量补齐任务的去重和可续跑；
- “未达到目标交易日”明确标记为 `STALE`，绝不标记为成功；
- 全部用户可见状态使用中文。

`H30533 中国互联网50` 的港股数据源与代码映射问题不在本次修复范围内；本次只保证其失败会被持久化和清楚展示。

## 方案选择

采用本地 SQLite 持久化运行记录，加 NiceGUI `background_tasks.create` 的服务端后台任务。

不采用仅查询 `data_update_state` 的轻量方案，因为它无法区分“当前运行中”“已完成”“被服务器中断”，也无法展示本次任务进度与摘要。也不引入外部队列，避免给单机系统增加部署和运维负担。

## 架构

### 运行记录

新增 `maintenance_task_run` 表，一行表示一次全量维护操作，字段包括：

- `task_id`：自增主键；
- `task_type`：稳定内部类型，例如 `index_history_batch`；
- `state`：内部值 `running`、`success`、`failed`、`interrupted`；
- `progress_done`、`progress_total`、`progress_detail`：当前处理进度；
- `result_json`：完整逐标的结果，供刷新后恢复摘要与结果表；
- `error_message`：任务级异常；
- `started_at`、`finished_at`、`updated_at`：任务时间线。

`data_fetch_job` 继续表示待执行的单标的历史任务；不混入一次全量运行的生命周期。

### 后台执行与恢复

新的维护任务协调器放在 `nicegui_app` 的独立模块中，维护当前进程内的活动任务 ID。点击全量指数补齐时：

1. 若已有 `index_history_batch` 处于运行中，页面绑定并展示该运行记录，不再创建第二个任务；
2. 否则创建运行记录，并通过 `background_tasks.create` 启动服务端协程；
3. 协程使用 `run.io_bound` 执行阻塞的数据服务；每处理一个指数，通过回调写入 SQLite 进度；
4. 成功、失败或服务器中断都会更新运行记录；页面刷新仅丢失客户端，不会中止后台协程；
5. 服务器重启后，内存中没有对应活动任务的 `running` 记录会在下次读取时标为“已中断”。用户再次点击会按本地历史新鲜度续跑。

页面加载时读取最近一次指数全量运行记录；运行中页面每秒读取一次 SQLite 状态并渲染任务中心。结果摘要和逐标的结果从 `result_json` 恢复，因此重新打开页面也能看到。

### 指数历史新鲜度

`InitializationService.ensure_index_history` 以 `expected_latest_trade_date(through)` 作为目标日期：

- 若已有文件达到目标日期，返回 `SKIPPED`；
- 若拉取后最新日期达到目标，记录 `SUCCESS` 并返回 `INITIALIZED` 或 `UPDATED`；
- 若没有新增记录，或合并后仍落后目标日期，记录 `STALE`，错误信息包含本地最新日与目标日；
- 若接口异常，记录 `FAILED`；空历史仍记录 `EMPTY`。

批量任务将 `UPDATED`、`INITIALIZED`、`SKIPPED`、`STALE`、`FAILED`、`EMPTY` 分别计数。页面使用“补齐”“跳过”“行情仍滞后”“失败/无数据”的中文摘要，避免把遍历完成误读为所有数据同步成功。

## 用户流程

1. 打开“数据维护 → 补齐任务 → 指数历史”，点击“一键初始化/补齐全部指数”。
2. 任务中心立即显示“运行中”和 `已完成 / 总数 · 当前指数 状态`。
3. 用户刷新页面或关闭后重新打开同一路径，任务中心恢复相同进度或最终结果。
4. 若进程仍在运行，重复点击只会回到已有任务；若服务器重启导致中断，页面显示“已中断”，再次点击从本地已补齐的数据继续。
5. 完成后页面刷新快照；数据体检按实际最新交易日显示“数据可用”“行情滞后”或“历史缺失”。

## 验收与测试

- SQLite 测试验证运行记录的创建、进度更新、结果恢复、失败与中断状态；
- 服务测试验证指数批量回调会逐项发送进度，空新增或未达到目标日返回 `STALE`，不再写 `SUCCESS`；
- NiceGUI 页面测试验证全量指数按钮绑定持久化任务、刷新后的任务中心可从运行记录恢复、同类运行任务不重复启动；
- 现有全量 pytest 回归；
- 浏览器验证：启动任务后刷新页面，确认进度或最终结果仍存在，并确认滞后项不会显示为成功。

## 范围边界

- 不增加第三方依赖，不改策略、回测或 ETF 批量任务的执行语义；
- 不自动重试 `H30533` 的不可用港股源；
- 不在服务器重启后隐式继续网络拉取，避免用户不知情的后台数据请求。
